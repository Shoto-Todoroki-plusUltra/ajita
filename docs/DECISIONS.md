# Design decisions and limitations

Phase 0 proposal revised 14 October 2026 after critical review. Architecture is provisionally accepted; Phase 1 implementation is not authorized. [PROJECT_BRIEF.md](../PROJECT_BRIEF.md) remains the controlling specification. No application work has started.

| Decision | Reason and trade-off | Review condition |
| --- | --- | --- |
| Assume no demonstrated practical quantum advantage; novelty unverified | Local simulation is classical computation. Existing QUBO/QAOA, MQT frameworks and classical systems overlap heavily with the vision. Useful engineering and reproducible negative results are legitimate outcomes. | Revise claims only after controlled evidence and a literature review; never infer speedup from circuit size or QUBO energy. |
| TSP before vehicle routing | One closed tour provides a small, inspectable objective and an exact permutation oracle. Fixing the depot reduces symmetry. CVRP adds vehicles, capacities, demands and route structure that need separate modeling/validation. | CVRP is a separately approved future phase, with first-class classical OR-Tools and specialized routing comparisons. |
| Native classical models, optional QUBO | OR-Tools routing and CP-SAT avoid forcing hard constraints into penalties. Classical-only jobs remain useful without quantum dependencies. | A transformation may return unsupported. Do not silently drop constraints or replace an unsupported problem with a different one. |
| Strict domain models and common verification/result contracts | Shared structure is enough for two domains. A universal optimization IR or speculative policy engine would expand the MVP and obscure domain semantics. | Refactor only when Phase 2 demonstrates a concrete need; retain all brief protocol methods. |
| Explicit reduced TSP QUBO plus optional Mapper cross-check | The small polynomial is auditable. Mapper is the recommended modeling successor; archived Optimization is no longer a required integration target. | All 512 reduced energies and feasible decodings must agree after matching penalties/order/offset; do not rely on converter status alone. |
| Upper-triangular QUBO with offset, scale and portable map | Eliminates off-diagonal factor ambiguity and supports energy round trips. Export is our format, not a standard. Auxiliary encodings can be many-to-one. | Reject unknown formats/decoders; validate original instance after interpretation. |
| Conservative sufficient TSP penalty | Nonnegative cost and integer one-hot residuals give a transparent separation proof with A greater than n times maximum distance. Large penalties can worsen numerical conditioning and QAOA optimization. | Test every tiny binary assignment and weak-penalty counterexamples; do not generalize the bound to arbitrary models. |
| Invalid samples remain visible; rank only feasible original objectives | A low-energy bitstring can violate hard constraints. Postselection changes the effective success rate and must be reported. | Count invalid shots in feasibility rates. No invisible repair, dropped failures or optimality claims without reference evidence. |
| Integer OR-Tools costs with explicit scale and original float scoring | Routing expects integer arc costs; rounding can affect rankings. A useful heuristic need not be an exact original-objective solver. | Test near-ties/overflow and document error bounds; exact oracle is the tiny original-objective reference. |
| One event per B1 course, discrete nonoverlapping slots, integer preferences | Keeps capacity and conflicts precise and allows exhaustive reference fixtures. It excludes durations, recurrence, complex calendars and individual student sectioning. | New semantics require a separate reviewed scope; do not imply UniTime feature parity. |
| Python 3.12 native arm64 virtual environment | Available locally and matches the brief. Default Python 3.14 is not the project target, although published wheels exist. Avoid Rosetta/mixed-architecture builds. | Resolve and smoke-test on actual Mac; published wheel tags alone are insufficient. |
| pip-tools hash locks, generated API types, small React/Vite UI | uv is not currently present; reproducibility matters more than a package-manager preference. No large UI framework, map service or Docker requirement. | Choose tool/package versions in approved Phase 1 and check supported Node pairing; keep platform locks explicit. |
| Bounded V2 local QAOA, initially four cities, after mathematical checkpoint | Mapper provides mapping rather than the old quantum solver stack. Direct core circuit/sampler APIs and a bounded SciPy loop supply execution independently. | Algorithm completion, feasible sampling and optimal sampling are distinct outcomes; none proves the formulation correct without 1A evidence. |
| Mathematical checkpoint before frontend/quantum integration | Exact routes, all-bit energy tests and independent validators are the admissions-relevant foundation. UI/framework work can obscure failures and consume the timeline. | Pause at 1A with executed evidence; quantum run quality is assessed separately at 1B, minimal product slice at 1C. |
| Cloud submission absent until Phase 4 | Credential, billing and plan permissions are unknown. IBM APIs and supported execution modes change. | Separate later phase approval from per-run affirmative authorization and charge review. No jobs or resources now. |

The [Architecture](ARCHITECTURE.md) gives mathematical contracts/limits; [Prior art](PRIOR_ART.md) records the three-way dependency comparison. The archived project's [official README](https://raw.githubusercontent.com/qiskit-community/qiskit-optimization/main/README.md) recommends Mapper; its [migration guide](https://qiskit.github.io/qiskit-addon-opt-mapper/how_tos/00_migrate_from_qiskit_optimization.html) excludes QAOA/optimizer/eigensolver migration. Therefore choose explicit reference math, optional Mapper modeling and direct Qiskit-core execution as separate boundaries. This supersedes the initial archived-library-first strategy. Mapper is officially supported but early pre-1.0; no formal experimental label was found, and stability must not be inferred. No dependency decision is runtime-validated yet.

## What the MVP will and will not establish

A complete Phase 1 slice should establish that one small TSP can travel through input, classical solving, optional QUBO/quantum execution, decoding, independent verification and UI reporting. It does not establish general QAOA convergence, practical quantum advantage, scalable optimization, production scheduling quality or road routing. Coordinates mean planar Euclidean distances; travel time requires separate licensed road/traffic data.

Runtime caps can reject otherwise mathematically supported instances. Compiling a 49-variable polynomial is much cheaper than a dense statevector calculation. Shots, depth and memory estimates describe resources, not performance guarantees. QAOA must be compared to credible classical solvers on the same original problem, not only a quantum exhaustive eigensolver.

The before-January-2027 objective is an intended deadline, not a delivery guarantee. The user has now provisionally reviewed the architecture; that is design review, not code review, runtime validation or Phase 1 authorization. Current unknowns include RAM/CPU details, package resolution, Mapper release/main differences, frontend runtime pairing and license choice.

## Workload and application-timeline priorities

Prioritize checkpoint 1A: one concrete synthetic matrix, strict minimal Python contracts, six-route optimum proof/oracle, OR-Tools baseline, nine-bit QUBO, all 512 energy/feasibility tests, route decoding, convention tests, portable artifact and an executed-command report. These are essential and achievable as small reviewable tasks without Qiskit, FastAPI, Node or browser dependencies. No task-hour estimates are asserted without a working environment.

After 1A review: direct core/Aer compatibility, optional Mapper equivalence, bounded QAOA and resource guard (1B), then minimal API and preset/result UI (1C). Defer broader matrix-import UI polish, large-instance tuning, exhaustive five-city expansion, optional archived comparisons, multi-platform certification and advanced dashboards until the core evidence exists. They remain explicit outstanding work where required by final Phase 1 acceptance; do not claim full Phase 1 completion early. Timetabling and cross-domain experiments keep their later phase gates.

For Master's application material, aim to freeze a reproducible evidence package by December 2026, leaving review time before January 2027; exact application deadlines are unknown. If time or compatibility is insufficient, present the verified 1A/1B subset honestly and list 1C/Phase 2/3 omissions. A smaller rigorous artifact is preferable to broad untested features. Reducing final phase requirements requires user scope revision; the checkpoint itself does not waive the brief's full vertical-slice gate.

## Research decision and known limitations

Adopt the provisional cross-domain question in PRIOR_ART: penalties versus feasible-shot fraction, original-objective quality and measured compilation resources under fixed budgets. Penalty tuning, feasible-subspace approaches and formulation comparisons already exist. The possible output is a reproducible characterization/negative result, not a new mechanism or a claim of novelty.

Separate ground-state preservation from optimizer behavior. In a fixed nonzero Ising interaction graph, increasing A need not increase qubits or gates; test coefficient/angle effects separately from new slack variables, structural cancellation and compiler choices. Count failed/no-feasible trials and charge tuning work to the experimental budget. A trend on a four-city fixture is not a transferable scheduling rule. Cross-domain conclusions require actual B1 evidence; otherwise label the study TSP-only.

## Future delivery-routing scope

Phase 1 cannot serve actual fleet dispatch. An asymmetric road matrix needs a separate schema/version and licensed source, directed objective/oracle tests, explicit unreachable arcs and loss of reversal symmetry. CVRP subsequently needs capacity/demand/vehicle semantics and native classical validation. Travel-time, traffic and time-window models extend scope further. Existing [OR-Tools capacity models](https://developers.google.com/optimization/routing/cvrp) and PyVRP are precedents; adding a Mapper `VehicleRouting` class does not establish equivalent CVRP semantics or scalability. Retain explicit unsupported QUBO cases. These are design transitions only, with no extensions authorized now.
